## 1. Короткий опис роботи

**OLTP (Online Transaction Processing)** — операційна обробка транзакцій у режимі реального часу. Це клас застосунків та запитів, орієнтованих на щоденну рутинну роботу з базою даних: читання записів, реєстрацію нових користувачів, оновлення лічильників переглядів, видалення спам-коментарів. Кожна така дія — це окрема OLTP-транзакція, яка має бути короткою, атомарною та надійною. Для відеохостинг-платформи **VideoHub** OLTP-навантаження формує основну активність користувачів: хтось відкриває сторінку каналу (SELECT), завантажує нове відео (INSERT), переглядає його й автоматично збільшує лічильник (UPDATE), а модератор прибирає недотепний коментар (DELETE).

У цій лабораторній роботі розглядаються чотири базові операції мови DML (Data Manipulation Language), які формують ядро будь-якого OLTP-застосунку:

- **SELECT** — вибірка даних за умовою `WHERE`, сортування `ORDER BY`, пошук за шаблоном `LIKE`.
- **INSERT** — додавання нових записів до таблиць `User` та `Video`.
- **UPDATE** — зміна значень існуючих записів (наприклад, збільшення кількості переглядів).
- **DELETE** — видалення записів за ідентифікатором (наприклад, коментаря).

Усі запити виконуються на канонічній схемі VideoHub з п'ятьма сутностями (`User`, `Video`, `Comment`, `Like`, `Subscription`) і чотирма зв'язками між ними. Робота виконувалась у СКБД PostgreSQL через інтерфейс pgAdmin, що дає змогу наочно побачити стан таблиць до та після кожної операції.

## 2. SELECT — вибірка даних

Команда `SELECT` призначена для отримання даних із таблиць без їхнього змінення. Це єдина DML-команда, яка не модифікує стан БД, а отже є безпечною для читання навіть під час активних транзакцій. В нашій схемі `SELECT` використовується для: переліку відео конкретного каналу, пошуку користувачів за доменом email, фільтрації публічних відео за кількістю переглядів, виводу коментарів до конкретного відео та отримання списку всіх каналів.

### 2.1 Запит 1 — Відео конкретного користувача

Запит вибирає всі відео користувача з `user_id = 1` і сортує їх за датою створення у порядку спадання (спочатку найновіші). Це типовий запит для сторінки каналу: коли відвідувач відкриває профіль автора, він хоче бачити свіжі завантаження першими.

```sql
SELECT video_id, title, views, is_public, created_at
FROM Video
WHERE user_id = 1
ORDER BY created_at DESC;
```

Конструкція `WHERE user_id = 1` фільтрує рядки таблиці `Video`, залишаючи лише ті, що належать першому користувачу. `ORDER BY created_at DESC` сортує результат за полем `created_at` у спадному порядку. Скріншот `select_1.png` демонструє результат виконання запиту.

### 2.2 Запит 2 — Користувачі з Gmail email

Цей запит ілюструє використання оператора `LIKE` для пошуку за шаблоном. Ми шукаємо всіх користувачів, чий email зареєстровано у домені `gmail.com`. Шаблон `%@gmail.com` означає: будь-яка послідовність символів перед `@gmail.com`. Знак `%` відповідає нулю або більше будь-яких символів.

```sql
SELECT user_id, username, email, created_at
FROM "User"
WHERE email LIKE '%@gmail.com';
```

Звернемо увагу на подвійні лапки навколо `"User"` — у PostgreSQL вони потрібні, оскільки `User` є зарезервованим словом, а лапки змушують СКБД трактувати ідентифікатор буквально як назву таблиці. Результат запиту представлено на скріншоті `select_2.png`.

### 2.3 Запит 3 — Публічні відео з переглядами більше 1000

Запит поєднує дві умови в `WHERE`: відео має бути публічним (`is_public = TRUE`) і мати понад 1000 переглядів (`views > 1000`). Результат сортується за кількістю переглядів у порядку спадання — це класичний «тренд»-список популярного контенту платформи.

```sql
SELECT video_id, title, views, duration_seconds
FROM Video
WHERE is_public = TRUE AND views > 1000
ORDER BY views DESC;
```

Логічний оператор `AND` гарантує, що рядок потрапить у результат лише за умови виконання обох предикатів одночасно. Це дає змогу відфільтрувати приватні відео (їх не треба показувати у загальній стрічці) і виключити малопереглянуті записи. Результат зображено на скріншоті `select_3.png`.

### 2.4 Запит 4 — Коментарі до конкретного відео

Запит вибирає всі коментарі до відео з `video_id = 1` і сортує їх за датою створення у порядку зростання (`ASC`) — тобто спочатку найстаріші, як це прийнято у стрічці коментарів. Звернемо увагу, що `ASC` є типово усталеним напрямком сортування, однак ми вказуємо його явно для читабельності.

```sql
SELECT comment_id, user_id, text, created_at
FROM Comment
WHERE video_id = 1
ORDER BY created_at ASC;
```

Поле `text` містить безпосередньо тіло коментаря, а `user_id` вказує на його автора. Цей запит лежить в основі віджету «Коментарі» на сторінці перегляду відео. Результат — на скріншоті `select_4.png`.

### 2.5 Запит 5 — Усі канали платформи

Запит повертає список користувачів, які мають статус каналу (`is_channel = TRUE`). Саме ці користувачі мають право завантажувати відео. Сортування за `created_at` без вказування напрямку дає усталений порядок зростання — від найстаріших каналів до найновіших.

```sql
SELECT user_id, username, email, bio, created_at
FROM "User"
WHERE is_channel = TRUE
ORDER BY created_at;
```

Цей запит формує каталог каналів платформи — сторінку, де відвідувачі можуть переглянути та обрати собі авторів на свій смак. Результат виконання зображено на скріншоті `select_5.png`.

## 3. INSERT — додавання нових даних

Команда `INSERT` додає нові рядки до таблиці. На відміну від `SELECT`, ця операція змінює стан БД і має бути виконана в рамках транзакції, щоб у разі помилки її можна було відкотити. У VideoHub типова послідовність реєстрації нового автора така: спершу додається запис про користувача, потім — його перше відео, причому другий `INSERT` посилається на `user_id`, згенерований першим.

### 3.1 Додавання нового користувача

Запит додає нового користувача з нікнеймом `new_user_test`, email `newuser@example.com`, хешем пароля, URL-адресою аватара та біографією. Поле `is_channel = TRUE` одразу надає йому статус каналу, тобто право завантажувати відео. Інші поля (`user_id`, `created_at`) заповнюються автоматично завдяки `BIGSERIAL` та `DEFAULT NOW()`.

```sql
INSERT INTO "User" (username, email, password_hash, avatar_url, bio, is_channel)
VALUES ('new_user_test', 'newuser@example.com', 'hash123', 'https://example.com/avatar.jpg', 'Новий тестовий користувач', TRUE);
```

Стан таблиці до операції фіксується на скріншоті `insert_before.png` — у списку ще немає користувача з нікнеймом `new_user_test`. Стан після виконання — на скріншоті `insert_after.png`: з'явився новий рядок, якому СКБД призначила чергове значення `user_id` (у нашому випадку 6).

### 3.2 Додавання нового відео

Цей `INSERT` логічно продовжує попередній: новостворений користувач (`user_id = 6`) завантажує своє перше відео. Запит вказує заголовок, опис, URL-адреси самого відео та обкладинки, тривалість у секундах, нульову початкову кількість переглядів та прапорець `is_public = TRUE`.

```sql
INSERT INTO Video (user_id, title, description, video_url, thumbnail_url, duration_seconds, views, is_public)
VALUES (6, 'Тестове відео', 'Опис тестового відео для лабораторної роботи 3', 'https://example.com/video.mp4', 'https://example.com/thumb.jpg', 120, 0, TRUE);
```

Важливо, що `user_id = 6` у другому запиті навмисно збігається з тим ідентифікатором, який отримав щойно створений користувач. У реальному застосунку цей ID отримують через `RETURNING user_id` або ORM-клієнт, але в межах лабораторної роботи ми припускаємо конкретне значення. Зовнішній ключ `video.user_id → "User".user_id` гарантує, що відео не можна привласнити неіснуючому користувачу — спроба зробити це викличе помилку порушення цілості посилання.

## 4. UPDATE — зміна існуючих даних

Команда `UPDATE` модифікує значення в уже наявних рядках. Це основна операція для всіх лічильників та станів: кількість переглядів зростає при кожному відкритті відео, статус `is_public` перемикається між публічним та приватним, біографія каналу оновлюється тощо. Ключове правило безпеки: `UPDATE` завжди має супроводжуватись `WHERE`, інакше зміни зачеплять усі рядки таблиці.

### 4.1 Збільшення кількості переглядів

Запит додає 100 до поточного значення `views` для відео з `video_id = 1`. Це імітація типової OLTP-операції «перегляд відео»: у реальному застосунку при кожному запуску плеєра виконується аналогічний запит з приростом на 1, а тут для наочності взято 100.

```sql
UPDATE Video
SET views = views + 100
WHERE video_id = 1;
```

Вираз `views = views + 100` у блоці `SET` означає «покласти у стовпець `views` його ж поточне значення плюс 100» — тобто відносний приріст, а не абсолютне присвоєння. Умова `WHERE video_id = 1` обмежує дію запиту єдиним рядком. Скріншоти `update_before.png` та `update_after.png` ілюструють стан відео до та після оновлення: значення `views` зростає рівно на 100.

<img src="screenshots/update_after.png" style="width: 100%; max-width: 800px;">

### 4.2 Небезпечний варіант без WHERE

У файлі `queries.sql` спеціально залишено закоментований «поганий» варіант:

```sql
-- УВАГА: Ніколи не робіть так! Цей запит оновить ВСІ відео в базі даних!
-- UPDATE Video
-- SET views = views + 100;
```

Без `WHERE` PostgreSQL застосує `SET` до кожного рядка таблиці. У результаті кількість переглядів збільшиться одразу у всіх відео платформи, що спотворить статистику та зіпсує рекомендаційну стрічку. Такий запуск є серйозною виробничою аварією.

## 5. DELETE — видалення даних

Команда `DELETE` вилучає рядки з таблиці. У нашій схемі видалення автоматично каскадується через `ON DELETE CASCADE`: коли видаляється коментар, нічого додаткового не відбувається; але коли видаляється користувач — автоматично прибираються всі його відео, коментарі, лайки та підписки. Це гарантує цілеспрямованість даних і запобігає появі «осиротілих» рядків.

### 5.1 Видалення конкретного коментаря

Запит вилучає з таблиці `Comment` рядок з `comment_id = 3`. Це типова дія модератора: користувач натискає «Поскаржитись», система перевіряє скаргу і, якщо коментар порушує правила, прибирає його саме цим запитом.

```sql
DELETE FROM Comment
WHERE comment_id = 3;
```

Умова `WHERE comment_id = 3` захищає від масового видалення. Скріншоти `delete_before.png` та `delete_after.png` показують таблицю `Comment` до та після операції: рядок з `comment_id = 3` зникає, інші рядки лишаються недоторканими.

<img src="screenshots/delete_before.png" style="width: 100%; max-width: 800px;">

<img src="screenshots/delete_after.png" style="width: 100%; max-width: 800px;">

### 5.2 Небезпечний варіант без WHERE

Як і у випадку з `UPDATE`, у файлі міститься закоментований «поганий» приклад:

```sql
-- УВАГА: Ніколи не робіть так! Цей запит видалить ВСІ коментарі з бази даних!
-- DELETE FROM Comment;
```

Без `WHERE` запит видаляє всі рядки таблиці `Comment`. Відновити дані після цього можна лише з резервної копії. На продакшн-системі така помилка означає втрату всієї історії коментарів платформи.

## 6. Перевірка результатів

Після кожної операції модифікації даних слід виконати перевірочний `SELECT`, щоб переконатись, що зміни відбулися саме ті, що очевувались. У файлі `queries.sql` передбачено чотири перевірки:

- Перевірка доданого користувача:

```sql
SELECT * FROM "User" WHERE username = 'new_user_test';
```

- Перевірка доданого відео:

```sql
SELECT * FROM Video WHERE user_id = 6;
```

- Перевірка оновлених переглядів:

```sql
SELECT video_id, title, views FROM Video WHERE video_id = 1;
```

- Перевірка видаленого коментаря (повертає порожній результат):

```sql
SELECT * FROM Comment WHERE comment_id = 3;
```

Останній запит повинен повернути нуль рядків — це й є підтвердження того, що видалення відбулося коректно. У цій роботі перевірки використовувались для знімання «після»-скріншотів: після `INSERT` виконувався відповідний `SELECT`, після `UPDATE` — повторне читання рядка з новим значенням `views`, після `DELETE` — спроба обрати неіснуючий уже запис.

Такий підхід — не просто ритуал, а робочий стандарт: будь-яка DML-операція в OLTP-застосунку повинна супроводжуватись перевіркою. В реальному коді VideoHub ця логіка реалізована у сервісному шарі, де після `prisma.comment.delete()` одразу йде `prisma.comment.findUnique()` для підтвердження, що запис справді зник, а на рівні бази для аудиту ведеться журнал операцій.

## 7. Попередження про WHERE без UPDATE/DELETE

Найнебезпечніша помилка в OLTP-роботі — виконати `UPDATE` або `DELETE` без умови `WHERE`. Наслідки:

- **`UPDATE ... SET ... ;` без WHERE** змінює всі рядки таблиці. Наприклад, `UPDATE Video SET views = 0;` обнулить лічильник переглядів усіх відео платформи, повністю зруйнувши статистику.
- **`DELETE FROM ...;` без WHERE** вилучає всі рядки таблиці. Наприклад, `DELETE FROM "User";` видалить усіх користувачів, а через `ON DELETE CASCADE` автоматично зникнуть усі відео, коментарі, лайки та підписки — база стане порожньою за мілісекунду.

Правила техніки безпеки, яких слід дотримуватись:

1. **Завжди писати `WHERE` першим**, ще до `SET` або `FROM`, і лише потім дописувати решту.
2. **Спершу виконати `SELECT` з тією ж умовою**, щоб побачити, які саме рядки будуть зачеплені. Скільки рядків поверне `SELECT` — стільки й змінить/видалить `UPDATE`/`DELETE`.
3. **Використовувати транзакції**: `BEGIN; ... ROLLBACK;` дає змогу відкотити небезпечну зміну, якщо щось пішло не так.
4. **У застосунку — параметризовані запити** з плейсхолдерами, щоб `user_id`, `comment_id` тощо ніколи не потрапляли в SQL через рядкову інтерполяцію.
5. **Резервні копії** — останній рубіж: навіть дотримуючись усіх правил, слід мати можливість відновити БД з бекапу.

У нашій схемі частина ризику пом'якшена обмеженнями: зовнішні ключі `ON DELETE CASCADE` захищають цілеспрямованість даних (не лишають «осиротілих» відео), `CHECK(views >= 0)` не дає зробити перегляди від'ємними, а `UNIQUE(email)` запобігає дублюванню користувачів. Однак жодне з цих обмежень не захищає від масового `UPDATE`/`DELETE` без `WHERE` — відповідальність за це лежить цілком на розробникові запиту.
