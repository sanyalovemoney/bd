## Мета роботи

Ознайомитися з аналітичними SQL-запитами (OLAP) до бази даних відеохостинг-платформи **VideoHub**. Опрацювати агрегатні функції (`COUNT`, `SUM`, `AVG`, `MIN`, `MAX`), конструкції `GROUP BY` та `HAVING`, різні типи `JOIN` (`INNER`, `LEFT`, `FULL OUTER`, `CROSS`), а також підзапити у clauses `SELECT`, `WHERE` та `HAVING`. Реалізувати запити на реальній схемі з п'яти сутностей: `Users`, `Videos`, `Comments`, `Likes`, `Subscriptions`.

---

## 1. OLAP проти OLTP — що таке аналітичні запити

**OLAP (Online Analytical Processing)** — це підхід до обробки даних, орієнтований на аналіз вже накопиченої інформації. На відміну від **OLTP (Online Transaction Processing)**, що обслуговує щоденні транзакції користувачів (завантаження відео, постановка лайка, додавання коментаря), OLAP фокусується на агрегації, групуванні та зіставленні великих масивів даних задля отримання бізнес-інсайтів.

Ключові відмінності:

- **OLTP** читає та змінює поодинокі рядки, гарантує транзакційність (ACID), оптимізований під швидкі вставки та оновлення. Приклад: `UPDATE videos SET views = views + 1 WHERE video_id = 5;`
- **OLAP** читає великі обсяги даних, зводить їх до кількох агрегованих рядків, майже не змінює дані. Приклад: `SELECT username, SUM(views) FROM Users JOIN Videos ... GROUP BY username;`

В межах цієї лабораторної жоден запит не модифікує дані — усі вони є аналітичними (тільки читання). СУБД: PostgreSQL, що підтримує повний набір OLAP-конструкцій включно з `FULL OUTER JOIN`, підзапитами та операціями над типом `NUMERIC`.

## 2. Агрегатні функції

Агрегатні функції беруть набір рядків і повертають одне підсумкове значення. Вони є основою будь-якого аналітичного запиту: без них неможливо побудувати звіти, KPI чи дашборди. Розглянемо п'ять основних агрегатів — `COUNT`, `SUM`, `AVG`, `MIN`, `MAX` — на прикладах із `queries.sql`.

### 2.1. COUNT — підрахунок записів

Функція `COUNT()` повертає кількість непорожніх значень (або рядків при `COUNT(*)`). У першому запиті з `queries.sql` ми рахуємо, скільки відео завантажив кожен канал:

```sql
SELECT
    u.username,
    COUNT(v.video_id) AS total_videos
FROM Users u
JOIN Videos v ON u.user_id = v.user_id
GROUP BY u.username
ORDER BY total_videos DESC;
```

**Що робить запит:** з'єднує таблиці `Users` та `Videos` за `user_id`, групує за `username`, підраховує кількість відео для кожного каналу та сортує за спаданням. Результат — рейтинг каналів за кількістю завантаженого контенту. Це типовий аналітичний запит: замість перегляду окремих відео ми отримуємо згорнуту метрику «активність каналу».

### 2.2. SUM — сума значень

Функція `SUM()` обчислює суму числового стовпця за групою. Наступний запит знаходить канали, сумарна кількість переглядів яких перевищує 1000:

```sql
SELECT
    u.username,
    SUM(v.views) AS total_channel_views
FROM Users u
JOIN Videos v ON u.user_id = v.user_id
GROUP BY u.username
HAVING SUM(v.views) > 1000
ORDER BY total_channel_views DESC;
```

**Що робить запит:** для кожного каналу підсумовує перегляди всіх його відео, за допомогою `HAVING` залишає лише ті групи, де сума перевищує 1000, і сортує за спаданням. Це дає звіт «топ-канали за загальною кількістю переглядів» — метрику, що показує не популярність окремого ролика, а сукупний охоп цілого автора.

<img src="screenshots/agg_sum.png" style="width: 100%; max-width: 800px;">

### 2.3. AVG — середнє значення

Функція `AVG()` обчислює середнє арифметичне. Запит нижче порівнює популярність каналів незалежно від кількості відео:

```sql
SELECT
    u.username,
    ROUND(AVG(v.views), 2) AS avg_views
FROM Users u
JOIN Videos v ON u.user_id = v.user_id
GROUP BY u.username
ORDER BY avg_views DESC;
```

**Що робить запит:** з'єднує користувачів із відео, групує за каналом, обчислює середнє значення стовпця `views` і заокруглює до двох знаків через `ROUND(..., 2)`. Середнє значення переглядів — більш справедлива метрика, ніж сума, адже вона не штрафує канали з малою кількістю відео. Запит аналітичний, бо згортує деталі окремих роликів до одного числа на канал.

<img src="screenshots/agg_avg.png" style="width: 100%; max-width: 800px;">

### 2.4. MIN та MAX — екстремальні значення

Функції `MIN()` та `MAX()` знаходять відповідно найменше та найбільше значення. Перший запит повертає діапазон тривалостей усієї платформи в один рядок:

```sql
SELECT
    MIN(duration_seconds) AS min_duration,
    MAX(duration_seconds) AS max_duration
FROM Videos;
```

**Що робить запит:** без `GROUP BY` агрегація відбувається над усією таблицею `Videos` одразу — отримуємо глобальний мінімум та максимум тривалості. Це корисно для перевірки консистентності даних (чи немає нульових чи аномально великих тривалостей) та для розуміння розмаху контенту на платформі.

Другий варіант — діапазон тривалостей для кожного каналу окремо:

```sql
SELECT
    u.username,
    MIN(v.duration_seconds) AS min_duration,
    MAX(v.duration_seconds) AS max_duration
FROM Users u
JOIN Videos v ON u.user_id = v.user_id
GROUP BY u.username
ORDER BY min_duration;
```

**Що робить запит:** те саме, але з `GROUP BY u.username` — тепер кожен канал має власний мінімум та максимум. Такий звіт показує, наскільки різноманітним є контент кожного автора: чи знімає він лише короткі ролики, чи_range широкий.

## 3. GROUP BY та HAVING

### 3.1. GROUP BY — групування для агрегації

Конструкція `GROUP BY` згортає рядки, що мають однакове значення у вказаному стовпці, в одну групу, над якою далі виконуються агрегатні функції. Без `GROUP BY` агрегати на кшталт `COUNT` чи `SUM` повертають єдиний рядок для всієї таблиці, а з `GROUP BY` — по одному рядку на кожну групу.

Наступний запит із `queries.sql` рахує кількість лайків для кожного відео:

```sql
SELECT
    v.title,
    COUNT(l.like_id) AS total_likes
FROM Videos v
LEFT JOIN Likes l ON v.video_id = l.video_id AND l.is_like = TRUE
GROUP BY v.video_id, v.title
ORDER BY total_likes DESC;
```

**Що робить запит:** через `LEFT JOIN` до кожного відео приєднуються лише ті записи з `Likes`, де `is_like = TRUE` (ігноруємо дизлайки). Далі групування відбувається за `video_id, v.title` (вказуємо й `v.title`, бо він є у `SELECT`, а не в агрегаті). `COUNT(l.like_id)` рахує кількість лайків. Ліве з'єднання гарантує, що відео без жодного лайка все одно потрапить у результат зі значенням `0` (через `COUNT` над `NULL`-стовпцем). Сортування за спаданням формує рейтинг найбільш уподобаних відео.

### 3.2. HAVING — фільтрація груп

Конструкція `HAVING` відфільтровує цілі групи вже **після** агрегації — на відміну від `WHERE`, що фільтрує рядки **до** групування. На `HAVING` не діє правило про відсутність агрегатів у `WHERE`: тут агрегати цілком дозволені.

Запит із `queries.sql`, що використовує `HAVING` для відбору лише «великих» каналів:

```sql
SELECT
    u.username,
    SUM(v.views) AS total_channel_views
FROM Users u
JOIN Videos v ON u.user_id = v.user_id
GROUP BY u.username
HAVING SUM(v.views) > 1000
ORDER BY total_channel_views DESC;
```

**Що робить запит:** спочатку збирає всі перегляди у групи за каналом (`GROUP BY u.username` + `SUM(v.views)`), а потім `HAVING SUM(v.views) > 1000` залишає лише ті групи, де сума перевищує поріг. `WHERE` тут не підійшов би, бо фільтрація залежить від агрегованого значення, якого ще не існує до `GROUP BY`. Результат — звіт про канали, що сумарно принесли понад 1000 переглядів. Це аналітичний запит, бо відповідає на бізнес-питання «хто наші топ-автори за охопом?».

## 4. JOIN — з'єднання таблиць

Зв'язки між сутностями VideoHub реалізовано через зовнішні ключі, але для аналітики рядки з різних таблиць треба з'єднувати. Розглянемо чотири типи `JOIN` на прикладах із `queries.sql`.

### 4.1. INNER JOIN

`INNER JOIN` повертає лише ті рядки, для яких є збіг за умовою з'єднання в обох таблицях. Рядки без пари з обох боків відкидаються.

```sql
SELECT
    v.title,
    u.username AS author
FROM Videos v
INNER JOIN Users u ON v.user_id = u.user_id
ORDER BY v.title;
```

**Що робить запит:** до кожного відео приєднує нікнейм його автора. Оскільки `Videos.user_id` має обмеження `NOT NULL` і є FK на `Users`, кожне відео гарантовано має автора — тому `INNER JOIN` тут не втрачає жодного відео. Проте користувачі без відео у результат не потраплять. Запит формує простий довідник «відео → автор», придатний для відображення на сторінці перегляду.

<img src="screenshots/inner_join.png" style="width: 100%; max-width: 800px;">

---

### 4.2. LEFT JOIN

`LEFT JOIN` (або `LEFT OUTER JOIN`) зберігає всі рядки лівої таблиці. Якщо для рядка лівої таблиці немає пари в правій — стовпці правої таблиці заповнюються `NULL`.

```sql
SELECT
    u.username,
    v.title AS video_title
FROM Users u
LEFT JOIN Videos v ON u.user_id = v.user_id
ORDER BY u.username, v.title;
```

**Що робить запит:** повертає **усіх** користувачів незалежно від того, чи завантажували вони відео. Якщо користувач не має жодного відео, стовпець `video_title` буде `NULL`. Цей запит корисний для виявлення «неактивних» каналів — користувачів, які зареєструвались, але нічого не завантажили. Саме завдяки `LEFT` (а не `INNER`) ми бачимо повну картину аудиторії платформи.

<img src="screenshots/left_join.png" style="width: 100%; max-width: 800px;">

---

### 4.3. FULL OUTER JOIN

`FULL OUTER JOIN` поєднує поведінку `LEFT` та `RIGHT` JOIN: повертає всі рядки з обох таблиць. Якщо збігу немає — стовпці протилежного боку заповнюються `NULL`.

```sql
SELECT
    u.username,
    v.title AS video_title
FROM Users u
FULL OUTER JOIN Videos v ON u.user_id = v.user_id
ORDER BY u.username, v.title;
```

**Що робить запит:** показує повну картину — всі користувачі та всі відео. Якщо користувач не має відео, `video_title` буде `NULL`; якщо відео чомусь не має автора (що в нашій схемі неможливо через `NOT NULL` FK, але в загальному випадку можливо) — `username` буде `NULL`. Це найповніше з'єднання, корисне для аудиту референційної цілісності: будь-який «сирота» відразу стає видимим.

<img src="screenshots/full_outer_join.png" style="width: 100%; max-width: 800px;">

### 4.4. CROSS JOIN

`CROSS JOIN` утворює декартів добуток: кожен рядок першої таблиці поєднується з кожним рядком другої. Якщо в першій 10 рядків, а в другій 20 — отримаємо 200. На практиці використовується для генерації всіх можливих комбінацій.

```sql
SELECT
    u.username,
    CASE WHEN v.is_public = TRUE THEN 'public'
         ELSE 'private'
    END AS video_status
FROM Users u
CROSS JOIN (SELECT DISTINCT is_public FROM Videos) v
ORDER BY u.username, video_status;
```

**Що робить запит:** будує матрицю «користувач × статус відео». Підзапит `(SELECT DISTINCT is_public FROM Videos)` вибирає унікальні значення прапорця публічності (на практиці `TRUE`/`FALSE`), а `CROSS JOIN` сполучає кожного користувача з кожним статусом. `CASE WHEN` перетворює булеве значення у зручний текст. Такий звіт може слугувати основою для побудови матриці звітів: для кожного користувача і кожного статусу відео — окрема клітина з метрикою.

## 5. Підзапити (Subqueries)

Підзапит — це запит, вкладений у зовнішній запит. Він може стояти в `SELECT`, `WHERE`, `HAVING` або `FROM`. Підзапити бувають некорельовані (виконуються один раз) та корельовані (залежать від рядка зовнішнього запиту і виконуються для кожного рядка окремо). Розглянемо приклади з `queries.sql`.

### 5.1. Підзапит у SELECT — частка переглядів каналу

Перший підзапит обчислює для кожного відео, який відсоток переглядів воно дає своєму каналу:

```sql
SELECT
    v.title,
    v.views,
    (SELECT SUM(v2.views) FROM Videos v2 WHERE v2.user_id = v.user_id) AS channel_total_views,
    ROUND(
        v.views::NUMERIC / NULLIF((SELECT SUM(v2.views) FROM Videos v2 WHERE v2.user_id = v.user_id), 0) * 100,
        2
    ) AS view_share_pct
FROM Videos v
ORDER BY view_share_pct DESC NULLS LAST;
```

**Що робить запит:** у третьому стовпці підзапит рахує суму переглядів усіх відео того ж каналу (фільтр `v2.user_id = v.user_id` посилається на зовнішній рядок `v.user_id`, тож це **корельований** підзапит). У четвертому стовпці ділимо перегляди конкретного відео на суму переглядів каналу і множимо на 100 — отримуємо частку у відсотках. Операція `::NUMERIC` перетворює `INTEGER` на точне число, щоб ділення не було цілим. `NULLIF(..., 0)` захищає від ділення на нуль (якщо канал не має переглядів — отримаємо `NULL`, а не помилку). `ORDER BY ... NULLS LAST` відкидає порожні значення у кінець списку. Це аналітичний запит: він показує «зіркові» відео, що формують основну тягу каналу.

### 5.2. Корельований підзапит у WHERE — відео вище середнього по каналу

Цей запит відбирає лише ті відео, перегляди яких перевершують середнє по своєму каналу:

```sql
SELECT
    v.title,
    u.username AS channel,
    v.views,
    (SELECT ROUND(AVG(v2.views), 2) FROM Videos v2 WHERE v2.user_id = v.user_id) AS channel_avg_views
FROM Videos v
JOIN Users u ON v.user_id = u.user_id
WHERE v.views > (SELECT AVG(v2.views) FROM Videos v2 WHERE v2.user_id = v.user_id)
ORDER BY v.views DESC;
```

**Що робить запит:** для кожного відео зовнішній запит обчислює `AVG(v2.views)` у тому ж каналі (`v2.user_id = v.user_id`) — це корельований підзапит у `WHERE`. Якщо перегляди відео перевершують цю середню — рядок потрапляє в результат. Третій стовпець (`SELECT ... AS channel_avg_views`) показує саме середнє для наочності, тож ми бачимо і саме відео, і його канал, і скільки треба було переглядів, щоб перевершити середнє. Це аналітичний запит, бо відповідає на питання «які відео є локальними хітами свого каналу?».

### 5.3. Підзапит у HAVING — канали з кількістю відео вище середньої

Третій підзапит фільтрує групи за агрегатом, який сам обчислюється іншим підзапитом:

```sql
SELECT
    u.username,
    COUNT(v.video_id) AS video_count
FROM Users u
JOIN Videos v ON u.user_id = v.user_id
GROUP BY u.username
HAVING COUNT(v.video_id) > (
    SELECT AVG(channel_video_count)
    FROM (
        SELECT COUNT(*) AS channel_video_count
        FROM Videos
        GROUP BY user_id
    ) AS sub
)
ORDER BY video_count DESC;
```

**Що робить запит:** внутрішній підзапит `(SELECT COUNT(*) ... GROUP BY user_id)` рахує кількість відео на кожному каналі. Цей набір рядків обгортається в `FROM (...) AS sub`, а зовнішній `SELECT AVG(...)` обчислює середню кількість відео на канал. Нарешті, `HAVING COUNT(v.video_id) > (...)` залишає лише ті канали, де кількість відео перевершує це середнє. Підзапит у `HAVING` **некорельований** — він обчислюється один раз, бо не посилається на зовнішній рядок. Запит відповідає на бізнес-питання «хто з авторів веде канал активніше за середнє по платформі?».

## 6. Багатотаблична агрегація

Цей запит із `queries.sql` об'єднує чотири таблиці одночасно і демонструє тонкощі агрегації при кількох паралельних зв'язках:

```sql
SELECT
    u.username AS channel,
    COUNT(DISTINCT l.like_id) AS total_likes,
    COUNT(DISTINCT c.comment_id) AS total_comments
FROM Users u
JOIN Videos v ON u.user_id = v.user_id
LEFT JOIN Likes l ON v.video_id = l.video_id AND l.is_like = TRUE
LEFT JOIN Comments c ON v.video_id = c.video_id
GROUP BY u.username
ORDER BY total_likes DESC, total_comments DESC;
```

**Що робить запит:** спочатку з'єднує `Users → Videos` через `JOIN`, а потім до кожного відео через `LEFT JOIN` приєднує лайки (`is_like = TRUE`) та коментарі. Коли ми приєднуємо дві незалежні таблиці до однієї базової, виникає ефект «вибуху» рядків: на одне відео з 5 лайками та 3 коментарями припадає 5×3 = 15 рядків у проміжному наборі. Через це `COUNT(l.like_id)` дав би завищене число (помножене на кількість коментарів). Саме тому використовується `COUNT(DISTINCT ...)` — він рахує унікальні `like_id` та `comment_id`, усуваючи дублікати від декартового добутку. Сортування за `total_likes DESC, total_comments DESC` формує рейтинг каналів за «залученістю» аудиторії. Це класичний приклад обережної багатотабличної агрегації, де нерозуміння природи JOIN могло б призвести до фатально хибних цифр у звіті.

## 7. Додаткові аналітичні запити

### 7.1. Загальний підсумок розмірів платформи

Запит нижче повертає єдиний рядок із чотирма метриками:

```sql
SELECT
    (SELECT COUNT(*) FROM Users) AS total_users,
    (SELECT COUNT(*) FROM Videos) AS total_videos,
    (SELECT COUNT(*) FROM Comments) AS total_comments,
    (SELECT COUNT(*) FROM Likes) AS total_likes;
```

**Що робить запит:** чотири незалежні підзапити в `SELECT` рахують кількість рядків у чотирьох основних таблицях. Кожен підзапит не корельований (не посилається на зовнішній запит) і виконується один раз. Результат — короткий зведений звіт про обсяг даних на платформі: скільки користувачів, відео, коментарів та лайків. Такий звіт зручно показати на дашборді адміністратора.

---

### 7.2. Топ-5 відео за кількістю коментарів

```sql
SELECT
    v.title,
    u.username AS channel,
    COUNT(c.comment_id) AS comment_count
FROM Videos v
JOIN Users u ON v.user_id = u.user_id
LEFT JOIN Comments c ON v.video_id = c.video_id
GROUP BY v.video_id, v.title, u.username
ORDER BY comment_count DESC
LIMIT 5;
```

**Що робить запит:** з'єднує відео з автором та коментарями, групує за відео, рахує кількість коментарів, сортує за спаданням і за допомогою `LIMIT 5` обрізає до п'ятірки найбільш коментованих. `LEFT JOIN` гарантує, що відео без коментарів теж потраплять у групування (з `comment_count = 0`), хоча в топ-5 вони навряд чи опиняться. Запит відповідає на питання «які відео викликали найбільше обговорення?» — це типова аналітична метрика «залученості».

---

### 7.3. Кількість підписників на кожен канал

```sql
SELECT
    u.username AS channel,
    COUNT(s.subscriber_id) AS subscriber_count
FROM Users u
LEFT JOIN Subscriptions s ON u.user_id = s.channel_id
GROUP BY u.username
ORDER BY subscriber_count DESC;
```

**Що робить запит:** до кожного користувача через `LEFT JOIN` приєднує записи з `Subscriptions`, де він є каналом (`channel_id = u.user_id`). `LEFT JOIN` гарантує, що користувачі без жодного підписника потраплять у результат із нулем. Групування за `username` та підрахунок `subscriber_id` дають рейтинг каналів за аудиторією. Цей запит відповідає на бізнес-питання «хто з авторів має найбільшу сталу аудиторію?» — показник, принципово важливий для монетизації та рекомендаційних алгоритмів платформи.

## Висновки

У межах лабораторної роботи №4 було опрацьовано повний інструментарій аналітичних SQL-запитів до бази даних відеохостинг-платформи **VideoHub**:

- Розглянуто відмінність між OLAP та OLTP — аналітичні запити читають та агрегують дані, тоді як транзакційні їх змінюють.
- Опановано п'ять агрегатних функцій: `COUNT`, `SUM`, `AVG`, `MIN`, `MAX` — на реальних прикладах з підрахунку відео, переглядів, лайків та тривалостей.
- Вивчено `GROUP BY` для згортання рядків у групи та `HAVING` для фільтрації вже агрегованих груп.
- Реалізовано чотири типи `JOIN`: `INNER` (лише збіги), `LEFT` (усі рядки з лівої таблиці), `FULL OUTER` (усі рядки з обох таблиць) та `CROSS` (декартів добуток).
- Опрацьовано підзапити у `SELECT`, `WHERE` та `HAVING`, як корельовані (залежні від зовнішнього рядка), так і некорельовані.
- Реалізовано багатотабличну агрегацію з `COUNT(DISTINCT)` для уникнення подвійного підрахунку при одночасному приєднанні кількох незалежних зв'язків.
- Побудовано додаткові аналітичні звіти: зведений підсумок платформи, топ-5 відео за коментарями, рейтинг каналів за підписниками.

Усі запити реальні — взято безпосередньо з файлу `queries.sql` проєкту VideoHub. Жоден запит не модифікує дані, що відповідає принципам OLAP. Набір запитів покриває основні аналітичні потреби платформи: від простих підрахунків до складних корельованих підзапитів, і може слугувати основою для адміністративного дашборду.
